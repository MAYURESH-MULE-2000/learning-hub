      The data analyst job, and what's expected

      A data analyst turns raw data into decisions. You pull data (SQL), clean and explore it (Excel, Power Query, SQL), model it and build reports people use every day (Power BI), and explain what it means in plain words. The tools are the easy half; asking the right question and telling a clear story is the job.

      Why this order: SQL, then Excel, then Power BI

      1. SQL first because almost every analyst interview starts with a SQL round, and every other tool gets its data from a database. Once you think in tables, joins and aggregations, Excel pivots and Power BI models feel obvious.
      2. Excel second because it's still where business lives: finance, operations, sales and HR all send you spreadsheets. Lookups, pivots and Power Query are tested in almost every interview.
      3. Power BI third because it builds on both: Power Query is the same engine you learn in Excel, the data model is the star schema you learn in SQL, and DAX is easier when you already understand grouping and filtering.

  customer_id   INT PRIMARY KEY,

CREATE TABLE products (
  product_id   INT PRIMARY KEY,
  product_name VARCHAR(100) NOT NULL,
  category     VARCHAR(50),
  sub_category VARCHAR(50),
  unit_price   DECIMAL(10,2),
  unit_cost    DECIMAL(10,2)

CREATE TABLE orders (
  order_id    INT PRIMARY KEY,
  customer_id INT REFERENCES customers(customer_id),
  order_date  DATE NOT NULL,
  ship_date   DATE,
  status      VARCHAR(20),
  channel     VARCHAR(20),
  region      VARCHAR(20)
);

  order_id   INT REFERENCES orders(order_id),
  product_id INT REFERENCES products(product_id),
  quantity   INT NOT NULL,

  discount   DECIMAL(4,2) DEFAULT 0,

);

      Thinking in data: tables, grain, dimensions and measures

      Before any formula, ask: what is one row? Most wrong numbers in reports come from misunderstanding the grain of a table, mixing up dimensions and measures, or double counting after a join.

      Vocabulary you'll use daily

      TermMeaningShopKart example
      GrainWhat one row representsorders: one row per order. order_items: one row per product in an order.
      DimensionSomething you group or filter by (text, dates, categories)city, category, channel, order month
      Measure / metricA number you aggregaterevenue, quantity, number of orders
      KPIA metric the business tracks against a targetmonthly revenue, average order value, repeat-customer rate
      Primary keyColumn(s) that uniquely identify a roworders.order_id; order_items has (order_id, product_id)
      Foreign keyColumn pointing to a key in another tableorders.customer_id → customers.customer_id
      Fact tableEvents/transactions with measures; many rowsorder_items (and orders)
      Dimension tableDescriptive attributes; fewer rowscustomers, products, a calendar table

      The metrics every analyst should define precisely

      • Revenue (net sales) = Σ quantity × unit_price × (1 − discount), usually excluding Cancelled and Returned orders. Always state what you excluded.
      • Orders = count of distinct order_id (not count of order_items rows).
      • Average order value (AOV) = revenue ÷ orders.
      • Gross profit = revenue − (quantity × unit_cost). Margin % = gross profit ÷ revenue.
      • Customers = count of distinct customer_id who ordered in the period.
      • Repeat rate = customers with 2+ orders ÷ customers with 1+ orders.
      • Growth % = (this period − last period) ÷ last period.

      The classic double-counting bug: joining orders (one row per order) to order_items (many rows per order) repeats each order's columns once per item. If you then SUM an order-level column (like a delivery fee), you multiply it. Always aggregate at the right grain.

      An analyst's workflow

      1. Clarify the question: who's asking, what decision depends on it, what time period, what counts.
      2. Find and understand the data: tables, grain, keys, known quirks.
      3. Extract and clean: SQL or Power Query; handle NULLs, duplicates, wrong types.
      4. Analyse: aggregate, compare periods and segments, look for outliers.
      5. Visualise and explain: the right chart, a clear headline, the "so what".
      6. Check: totals reconcile with a trusted source; spot-check a few rows by hand.

      Practice

      What is the grain of order_items, and why does it matter for counting orders?

      One row per product within an order. Counting rows counts lines, not orders, so to count orders you need COUNT(DISTINCT order_id).

      Is "region" a dimension or a measure? What about "discount"?

      Region is a dimension (you group by it). Discount is a numeric attribute of a line; you'd use it inside a measure calculation (revenue) or average it, but it's not something you'd sum on its own.

      Should a Cancelled order count toward revenue?

      Usually not: no money was collected. Many companies also exclude Returned orders from net revenue. The important thing is to decide explicitly and write the rule in your report notes.

      SQL foundations

      Reading data out of one table: SELECT, filtering, sorting, CASE, built-in functions, and turning rows into summaries with GROUP BY. This is 60% of all the SQL you'll ever write.

      What SQL is, and how a query runs

      SQL (Structured Query Language) is how you ask a database questions. You describe what you want ("total revenue per city, highest first"), and the database works out how to get it. You don't write loops.

      The shape of almost every query

      sql
      SELECT   columns or calculations     -- what to show
FROM     table                       -- where the data lives
WHERE    row filter                  -- which rows to keep
GROUP BY columns                     -- how to summarise
HAVING   group filter                -- which groups to keep
ORDER BY columns                     -- how to sort
LIMIT    n;                          -- how many rows to return

      Written order vs the order the database runs it

      You write SELECT first, but the database evaluates it in this logical order. Knowing this explains most "why doesn't this work?" errors.

      StepClauseConsequence
      1FROM / JOINBuild the working set of rows
      2WHEREFilter rows. Can't use column aliases from SELECT, can't use aggregates like SUM
      3GROUP BYCollapse rows into groups
      4HAVINGFilter groups. Can use aggregates
      5SELECTCompute output columns and aliases (window functions run here)
      6DISTINCTRemove duplicate output rows
      7ORDER BYSort. Can use aliases from SELECT
      8LIMIT / OFFSETCut the result

      "What is the order of execution of a SQL query?" is one of the most common SQL interview questions. Answer with the table above and give one consequence, e.g. "that's why I can't filter on a SUM in WHERE; I use HAVING".

      Style that makes queries readable

      • Keywords in UPPER CASE, table and column names in lower_snake_case.
      • One clause per line; indent continuation lines.
      • End statements with ;.
      • Comments: -- single line and /* multi-line */.
      • SQL keywords are case-insensitive. Text values inside quotes are case-sensitive in PostgreSQL ('Delhi' ≠ 'delhi'), but usually not in MySQL and SQL Server (depends on collation).

      Keys and relationships

      Data is split across tables so each fact is stored once. Keys connect them back together: a primary key identifies a row, a foreign key points at a primary key in another table.
      RelationshipShopKart exampleHow it's stored
      One-to-manyOne customer → many ordersorders.customer_id references customers.customer_id
      Many-to-manyOrders ↔ productsA bridge table, order_items, with both keys

      Why split? If customer names lived inside every order row, renaming a customer would mean updating hundreds of rows, and any missed row would disagree. This is normalisation (covered in the Databases part). The cost: you need joins to put the picture back together.

      Join pitfalls that produce wrong numbers

      1. Fan-out: totals get multiplied

      sql
      -- Imagine each order had a delivery fee of 50 stored on the orders table.
-- ❌ Joining to lines first repeats the fee once per line:
SELECT SUM(50) AS fee_wrong
FROM orders o JOIN order_items oi ON oi.order_id = o.order_id;
      Result 1 row
      fee_wrong
      1550
      sql
      -- ✅ Aggregate at the orders grain:
SELECT SUM(50) AS fee_right FROM orders;
      Result 1 row
      fee_right
      1000

      31 lines vs 20 orders. The fix is always: aggregate each table at its own grain (in a subquery or CTE), then join the summaries.

      2. A WHERE filter that cancels your LEFT JOIN

      sql
      -- ❌ The WHERE removes customers with no orders (their o.status is NULL) → behaves like INNER JOIN
SELECT c.customer_name, COUNT(o.order_id)
FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.status = 'Delivered'
GROUP BY c.customer_name;

-- ✅ Put conditions on the right-hand table inside ON
SELECT c.customer_name, COUNT(o.order_id)
FROM customers c LEFT JOIN orders o ON o.customer_id = c.customer_id AND o.status = 'Delivered'
GROUP BY c.customer_name;

      3. Duplicate keys in a lookup table

      If a "dimension" table has two rows for the same key (e.g. a product listed twice), every fact row joins to both and totals double. Before joining, check uniqueness:

      sql
      SELECT product_id, COUNT(*) FROM products GROUP BY product_id HAVING COUNT(*) > 1;   -- should return nothing
      Result 0 rows
      product_idcount_star()

      4. Joining on the wrong column or type

      Joining text '00123' to number 123, or mismatched codes with trailing spaces, silently drops rows. Compare row counts before and after each join; it's the fastest bug detector there is.

      "How do you check a query's result is right?" Row counts at each step, totals reconciled against a known source, a few rows checked by hand, and checking for duplicate keys before joins.

      Window functions: the idea, and ranking

      A window function calculates across related rows without collapsing them. GROUP BY gives one row per group; a window function keeps every row and adds a column like "rank within category" or "running total so far".
      text
      function(...) OVER (
    PARTITION BY ...   -- restart the calculation for each group (optional)
    ORDER BY ...       -- order rows inside the group (needed for ranking / running totals)
    ROWS BETWEEN ...   -- which rows around the current one to include (optional frame)
)

      Frames: ROWS vs RANGE

      FrameMeaning
      ROWS BETWEEN 2 PRECEDING AND CURRENT ROWThis row and the 2 before it: a 3-row moving window
      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROWEverything so far (running total)
      ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWINGCentred 3-row window
      Default with ORDER BYRANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW: rows with the same ORDER BY value are treated together, so ties jump at once

      If your running total jumps by two days' worth at once, you have duplicate dates and the default RANGE frame. Write ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW explicitly, or aggregate to one row per date first.

      Normalisation and the star schema

      Two ways to shape the same data. Normalised (OLTP) schemas store each fact once, ideal for the apps that write data. Star schemas (OLAP) organise data for analysis, and they're exactly what Power BI wants.

      Normal forms in plain words

      • 1NF: one value per cell (no "Mouse, Keyboard" in a single column), no repeating column groups (phone1, phone2, phone3).
      • 2NF: every non-key column depends on the whole key. In order_items (key = order_id + product_id), product_name depends only on product_id, so it belongs in products.
      • 3NF: no column depends on another non-key column. City → state relationships belong in a cities table, not repeated in every customer row (in practice many teams keep this one denormalised).

      OLTP vs OLAP

      OLTP (transactional)OLAP (analytical)

      ShapeNormalised, many tablesStar schema: facts + dimensions
      ExamplesPostgreSQL, MySQL, SQL ServerSnowflake, BigQuery, Redshift, Databricks, Microsoft Fabric, SQL Server warehouses

      Indexes and query performance

      An index is like the index at the back of a book. Instead of reading every page (a full table scan), the database jumps to the rows it needs.
      sql
      CREATE INDEX idx_orders_customer ON orders (customer_id);
CREATE INDEX idx_orders_date     ON orders (order_date);
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date);   -- composite: order matters
      • Index columns used in WHERE, JOIN … ON and ORDER BY on large tables.
      • A composite index on (customer_id, order_date) helps "this customer's orders by date", not "all orders on a date".
      • Indexes speed up reads but slow down inserts/updates and use space.
      • Clustered vs non-clustered (SQL Server): the clustered index is the table's physical order (usually the primary key); there's one per table.

      Reading a query plan

      sql
      EXPLAIN ANALYZE                       -- PostgreSQL: shows the plan and real timings
SELECT * FROM orders WHERE customer_id = 7;
-- SQL Server: "Include Actual Execution Plan" (Ctrl+M) in SSMS. MySQL: EXPLAIN ...

      Look for "Seq Scan" / "Table Scan" on large tables where you expected an index, and huge row estimates in joins.

      Habits that make queries fast

      • Select only the columns you need.
      • Filter early (in WHERE, or inside CTEs before joining).
      • Don't wrap indexed columns in functions in WHERE: WHERE order_date &gt;= '2026-03-01', not WHERE YEAR(order_date) = 2026.
      • UNION ALL instead of UNION when duplicates aren't possible.
      • EXISTS instead of COUNT(*) &gt; 0 to check existence.
      • Avoid SELECT DISTINCT as a band-aid for duplicate rows; fix the join.
      • Leading wildcards (LIKE '%desk') can't use a normal index.
      • On cloud warehouses (BigQuery, Snowflake) you pay per data scanned: filter on partition columns (dates) and avoid SELECT *.

      Conceptual questions with crisp answers

      WHERE vs HAVING?

      WHERE filters rows before grouping and can't use aggregates; HAVING filters groups after GROUP BY and usually uses aggregates.

      INNER vs LEFT JOIN?

      INNER returns only matching rows. LEFT returns every row from the left table, with NULLs for right-side columns when there's no match.

      UNION vs UNION ALL?

      UNION removes duplicates (extra sort/hash work); UNION ALL keeps all rows and is faster.

      COUNT(*) vs COUNT(column) vs COUNT(DISTINCT column)?

      All rows; non-NULL values in that column; unique non-NULL values.

      RANK vs DENSE_RANK vs ROW_NUMBER?

      RANK leaves gaps after ties (1,1,3), DENSE_RANK doesn't (1,1,2), ROW_NUMBER gives unique numbers even for ties (1,2,3).

      Primary key vs unique key?

      Both enforce uniqueness. A table has one primary key and it can't be NULL; it can have several unique keys, which usually allow NULL.

      DELETE vs TRUNCATE vs DROP?

      DELETE removes chosen rows (logged, filterable); TRUNCATE removes all rows fast; DROP removes the table itself.

      What is a CTE, and how is it different from a temp table or view?

      A CTE is a named subquery that exists only for one statement. A temp table stores data for the session. A view is a saved query stored in the database for everyone.

      Window function vs GROUP BY?

      GROUP BY collapses rows into one per group. A window function computes across a set of rows but keeps every row, adding the result as a column.

      What is an index? Downsides?

      A data structure that lets the database find rows without scanning the table, like a book index. It speeds up reads but slows writes and uses storage.

      What's normalisation? When would you denormalise?

      Organising data so each fact is stored once, reducing redundancy and update errors. Denormalise for analytics/reporting (star schemas) where read speed and simplicity matter more.

      What does SELECT NULL = NULL return?

      NULL (unknown), not true. Use IS NULL, or IS NOT DISTINCT FROM to compare values that may be NULL.

      Correlated vs non-correlated subquery?

      A non-correlated subquery runs once and doesn't reference the outer query. A correlated one references outer columns and is (logically) evaluated per outer row.

      What is a self join? Example?

      A table joined to itself using aliases, e.g. employees joined to employees to show each person's manager.

      Fact vs dimension table?

      Facts hold measurable events at a defined grain with keys to dimensions (order lines). Dimensions hold descriptive attributes used for filtering and grouping (products, customers, dates).

      The workhorses of reporting. "Total revenue for Furniture in the West in March" is one SUMIFS. Learn the argument order and the criteria syntax and you'll use them daily.

      Lookups: VLOOKUP, INDEX/MATCH and XLOOKUP

      Lookups bring a value from another table (the Excel version of a SQL join). Know all three: XLOOKUP for new work, INDEX/MATCH for older Excel, VLOOKUP because every interviewer and old workbook still uses it.

      For these examples, load products.csv as a second table named Products.

      VLOOKUP

      excel
      =VLOOKUP(lookup_value, table, column_number, FALSE)
=VLOOKUP(L2, Products, 6, FALSE)      // unit_cost is the 6th column of Products
      • Always pass FALSE (exact match). The default TRUE does an approximate match and silently returns wrong values on unsorted data.
      • Only looks to the right: the lookup column must be the first column of the table.
      • The column number is hard-coded: insert a column and it returns the wrong field.
      • Returns the first match only. #N/A = not found (often a space or number-stored-as-text issue).

      INDEX / MATCH

      excel
      =INDEX(return_range, MATCH(lookup_value, lookup_range, 0))
=INDEX(Products[unit_cost], MATCH(L2, Products[product_id], 0))

// Two-way lookup: value at the intersection of a row label and a column label
=INDEX(Grid, MATCH("West", RegionList, 0), MATCH("Furniture", CategoryList, 0))

      Works left or right, doesn't break when columns move, and was the "pro" choice before XLOOKUP. MATCH(..., 0) means exact match.

      excel

      Excel interview questions

      VLOOKUP vs XLOOKUP vs INDEX/MATCH?

      VLOOKUP looks right only, uses a hard-coded column number and defaults to approximate match. INDEX/MATCH looks in any direction and survives inserted columns. XLOOKUP does both with simpler syntax, exact match by default, a built-in not-found value, and search from the bottom, but needs Excel 2021/365.

      Relative vs absolute references?

      Relative (A1) shifts when copied; absolute ($A$1) stays fixed; mixed ($A1, A$1) fixes column or row. F4 cycles through them.

      How do you remove duplicates while keeping the original data?

      =UNIQUE() in a new place, Power Query Remove Duplicates, or copy the data and use Data → Remove Duplicates on the copy. Before removing, decide which columns define a duplicate.

      SUMIF vs SUMIFS?

      SUMIF takes one condition with the sum range last; SUMIFS takes many conditions with the sum range first. Use SUMIFS everywhere for consistency.

      What is a PivotTable and what are its limitations?

      An interactive summary (group, aggregate, filter) of a table. Limitations: needs manual refresh, calculated fields work on sums not rows, and source data must be clean and tabular.

      How would you find which rows exist in sheet A but not sheet B?

      =ISNA(MATCH(A2, SheetB!A:A, 0)) or =COUNTIF(SheetB!A:A, A2)=0 as a helper column, or =FILTER(A, ISNA(XMATCH(A, B))), or Power Query Merge with Left Anti join.

      What's Power Query and why use it over formulas?

      A recorded, repeatable data-preparation tool: import, clean, reshape and combine data with steps that re-run on Refresh. It handles messy and large data better than formulas and keeps the workbook simpler.

      How do you handle errors in a lookup?

      XLOOKUP's if_not_found argument, or IFNA around VLOOKUP/INDEX-MATCH. Then investigate why values are missing (spaces, text vs number, genuinely absent).

      What does Ctrl + Shift + Enter do?

      In older Excel it entered an array formula (shown with curly braces). In Microsoft 365, dynamic arrays make it unnecessary: array formulas just work and spill.

      What's conditional formatting with a formula? Example.

      A rule that formats cells when a formula returns TRUE, e.g. select the data and use =$D2="Cancelled" to highlight whole rows of cancelled orders.

      Power Query in Power BI

      It's the same Power Query you learned in Excel (Get Data, Applied Steps, Merge, Append, Unpivot, M), with a few Power BI specifics.

      Power BI specifics

      • Enable load (right-click a query): untick for staging queries that only feed others. Fewer tables, smaller model.
      • Data source settings (Transform Data → Data source settings): change file paths or server names and credentials in one place.
      • Parameters: store the folder path or server name as a parameter; switch dev/prod by changing one value.
      • Query folding: with databases, Power Query translates steps into SQL that runs on the server. Right-click a step → "View Native Query" (if available, it folded). Do filtering and column removal early, before steps that break folding (like adding an index column or custom M functions).
      • Column profiling (View → Column quality / distribution / profile): see errors, empty values and distinct counts instantly. Set profiling to "entire data set" at the bottom-left for accuracy.
      • Incremental refresh (for big tables): refresh only recent data; needs RangeStart/RangeEnd parameters.

      Shaping rules that make models fast and simple

      1. Remove columns you won't use (the biggest single performance win).
      2. Set correct data types; avoid "Any" type.
      3. Build fact tables at one grain; move descriptive text into dimension tables.
      4. Unpivot wide data (months as columns) into long format.
      5. Prefer doing row-level calculations in the source (SQL view) or Power Query rather than DAX calculated columns.
      6. Name queries and columns for business users: Customer City, not cust_cty_cd.

      Model hygiene checklist

      • Dimension keys are unique (a duplicate product_id makes the relationship many-to-many and breaks totals).
      • Hide foreign-key columns on the fact table (right-click → Hide in report view) so users slice by the dimension's columns.
      • Set Sort by column: month name sorted by month number (Column tools → Sort by column), otherwise Apr comes before Jan.
      • Set data categories (City, State, Country) so map visuals geocode correctly.
      • Set default summarisation to "Don't summarize" for IDs and years, so they're not accidentally summed.
      • Format measures once in the model (currency, decimals); every visual inherits it.
      • Group measures in display folders or a dedicated empty "_Measures" table.
      • Avoid bi-directional relationships and calculated columns unless needed.

      Common modelling situations

      • Two date columns (order_date, ship_date): one active relationship to Calendar, one inactive; use USERELATIONSHIP in "Revenue by Ship Date".
      • Targets at month × region grain and sales at day × product grain: relate both facts to shared dimensions (Calendar, Region) and compare in measures. Don't join facts to each other.
      • Header/detail facts (orders and order_items): flatten into one fact at line grain (as in the first build), allocating any order-level amounts.
      • Snowflaked dimensions (product → category table): merge into one product dimension in Power Query.

      "Why is a star schema recommended in Power BI?" Simpler DAX, correct filter propagation (dimensions filter facts), better compression and faster queries, and a model business users can understand.

      DAX basics: measures, calculated columns and tables

      A measure is a formula evaluated at query time for whatever filters are active (a cell in a visual, a slicer selection). A calculated column is computed once per row at refresh and stored. Use measures for numbers you aggregate; columns only for attributes you slice by.

      Syntax and conventions

      dax

CALCULATE (                                 -- function
    SUM ( Sales[net_amount] ),              -- Table[Column]
    Sales[status] IN { "Delivered", "Shipped" }   -- filter argument
)
// Reference other measures with brackets only:  [Revenue]
// Reference columns always with the table:      Sales[net_amount]
      • Always create explicit measures instead of dragging a column into Values (an "implicit" sum). Explicit measures are reusable, formatted once and required for many features.
      • Build small measures and combine them: [Revenue], [Cost], then Gross Profit = [Revenue] - [Cost].
      • Format with daxformatter.com-style indentation for anything longer than a line.
      • Use DIVIDE(a, b) instead of a / b: it returns BLANK instead of an error when b is zero.
      • Comments: -- or // for one line, /* */ for blocks.

      Row context, filter context and context transition

      Context is the single most important idea in DAX. Filter context = which rows are visible right now (from slicers, rows/columns of a visual, filters). Row context = "the current row" while iterating. Once these click, DAX stops being mysterious.

      Filter context

      In a matrix with categories on rows, the cell for Furniture computes [Revenue] with a filter products[category] = "Furniture". That filter flows through the relationship from products to Sales, so only Furniture lines are summed. The total row has no category filter, so it sums everything. The measure is the same; the context changes.

      text
      Visual cell for "Furniture, West, 2026"
  filter context = { products[category]="Furniture", Sales[region]="West", Calendar[Year]=2026 } + slicers + page/report filters
  [Revenue] then sums Sales[net_amount] over the rows that survive those filters

      Row context

      Calculated columns and iterator functions (SUMX, AVERAGEX, FILTER, RANKX…) walk a table row by row. Inside them, Sales[quantity] means "this row's quantity".

      dax
      -- Iterator: for each row of Sales, compute quantity × cost, then sum
Cost (simple) = SUMX ( Sales, Sales[quantity] * RELATED ( products[unit_cost] ) )
-- RELATED follows a many-to-one relationship from the current row to the dimension

      Row context does not filter anything by itself. In a calculated column, = SUM(Sales[net_amount]) returns the grand total on every row, because no filter is applied.

      Context transition

      When you call a measure (or wrap an expression in CALCULATE) inside a row context, the current row becomes a filter. That's context transition.

      dax
      -- Calculated column on customers: each customer's revenue
Customer Revenue = [Revenue]      -- works: the measure has an implicit CALCULATE,
                                  -- so the current customer row becomes a filter on Sales

-- Average revenue per customer (iterate customers, evaluate the measure for each)
Avg Revenue per Customer = AVERAGEX ( VALUES ( customers[customer_id] ), [Revenue] )

      Context transition inside iterators over large fact tables is expensive and can give surprising results if rows aren't unique. Iterate over a dimension (customers, products) rather than the fact table when you call measures inside SUMX/AVERAGEX.

      Aggregations and iterators

      FunctionDoes
      SUM, AVERAGE, MIN, MAXAggregate one column
      COUNTROWS(table)Rows in a table (preferred over COUNT for "how many rows")
      DISTINCTCOUNT(col)Unique values
      COUNT, COUNTA, COUNTBLANKNon-blank numbers / values / blanks in a column
      SUMX(table, expr), AVERAGEX, MINX, MAXX, COUNTXEvaluate an expression per row, then aggregate
      DIVIDE(a, b, [alt])Safe division
      RELATED(col)Get a value from the "one" side (lookup) inside row context
      RELATEDTABLE(table)Get the related rows from the "many" side
      dax
      -- Revenue computed from raw columns (if you hadn't made net_amount in Power Query)
Revenue (iter) = SUMX ( Sales, Sales[quantity] * Sales[unit_price] * ( 1 - Sales[discount] ) )

-- Average ORDER value vs average LINE value
Avg Line Value  = AVERAGE ( Sales[net_amount] )                                -- per line
Avg Order Value = AVERAGEX ( VALUES ( Sales[order_id] ), CALCULATE ( SUM ( Sales[net_amount] ) ) )   -- per order

-- Number of lines with a discount
Discounted Lines = COUNTROWS ( FILTER ( Sales, Sales[discount] > 0 ) )

-- Calculated column on products: units sold of this product
Units Sold = SUMX ( RELATEDTABLE ( Sales ), Sales[quantity] )

      SUM vs SUMX: SUM(col) is just SUMX(table, col) for a single column. Use SUMX when the thing you add up is an expression across columns.

      CALCULATE and filter functions

      CALCULATE(expression, filters…) evaluates an expression in a modified filter context. It's how you say "revenue, but only for Web", "revenue ignoring the category filter", "last year's revenue". Nearly every interesting measure uses it.
      dax
      Web Revenue      = CALCULATE ( [Revenue], Sales[channel] = "Web" )               -- adds/replaces a filter
Big-Order Rev    = CALCULATE ( [Revenue], Sales[net_amount] >= 10000 )
Furniture or Web = CALCULATE ( [Revenue], FILTER ( Sales, RELATED ( products[category] ) = "Furniture" || Sales[channel] = "Web" ) )

      How CALCULATE treats filters

      • A filter on a column replaces any existing filter on that same column. In a matrix by channel, Web Revenue shows the Web number on every row, including the App row.
      • Filters on different columns are combined with AND.
      • KEEPFILTERS(Sales[channel] = "Web") intersects instead of replacing: on the App row it returns blank.
      • Boolean filters (Sales[channel] = "Web") are shortcuts for FILTER(ALL(Sales[channel]), Sales[channel] = "Web").

      Removing filters: % of total patterns

      dax

      ALLSELECTED(...)Remove filters coming from the visual, but keep slicer/page selections: "% of what I'm looking at"

      REMOVEFILTERS(...)Clearer name for ALL inside CALCULATE
      VALUES(col)Distinct visible values of a column (respects filters)
      FILTER(table, condition)Row-by-row filtered table; needed for conditions across columns or on measures

      Time intelligence

      These functions need a marked date table related to your fact table, and visuals that use the Calendar's columns (not Sales[order_date]) on the axis.

      dax

Revenue PM        = CALCULATE ( [Revenue], DATEADD ( Calendar[Date], -1, MONTH ) )

CALCULATE (
    [Revenue],
    DATESINPERIOD ( Calendar[Date], MAX ( Calendar[Date] ), -3, MONTH )
)

    [Revenue],
    FILTER ( ALL ( Calendar[Date] ), Calendar[Date] <= MAX ( Calendar[Date] ) )

      7. Explain SUM vs SUMX with an example.

      SUM adds one column. SUMX evaluates an expression for each row of a table and adds the results, e.g. SUMX(Sales, Sales[quantity] * Sales[unit_price]). Multiplying two SUMs instead (SUM(qty) * SUM(price)) gives a wrong total.

      Publishing, sharing, refresh and security

      Publishing and sharing

      • Publish (Home → Publish) uploads the report and its semantic model to a workspace.
      • Workspaces are team areas with roles: Admin, Member, Contributor, Viewer. Keep "My workspace" for personal drafts.
      • Apps: bundle reports from a workspace for a wide audience; update the app when ready (a simple dev → publish flow).
      • Other ways: share a single report, embed in Teams/SharePoint, subscriptions (emailed snapshots), data alerts on dashboard tiles, Analyze in Excel (a PivotTable on the semantic model).
      • Publish to web creates a public link anyone on the internet can see. Never use it for company data; admins often disable it.
      • Deployment pipelines (Dev → Test → Prod) and Git integration with .pbip files exist for larger teams.

      Refresh

      • Imported data is a snapshot. Set scheduled refresh on the semantic model's settings (the number of daily refreshes depends on licence/capacity).
      • Cloud sources (SharePoint, Azure SQL) refresh directly; on-premises sources (a server in the office, files on a local drive) need an on-premises data gateway.
      • Files: store source Excel/CSV files in SharePoint/OneDrive, not on your laptop, so the service can reach them.
      • Check refresh history and set failure notifications; a dashboard silently showing last month's data destroys trust.

      Performance and best practices

      Find what's slow

      • Performance Analyzer (Optimize/View tab): start recording, refresh visuals, see DAX query time vs visual rendering per visual. Copy the query into DAX query view or DAX Studio to tune it.
      • DAX Studio and VertiPaq Analyzer (free tools): which columns use the most memory, server timings for queries.
      • Best Practice Analyzer in Tabular Editor: automated model checks.

      Make it fast

      1. Remove unused columns and rows, especially high-cardinality text (IDs, comments, timestamps with seconds). Split date-time into date and time if you need both.
      2. Star schema, single-direction relationships, integer keys.
      3. Prefer measures over calculated columns; do row-level work in Power Query or the source.
      4. Turn off Auto date/time; use one date table.
      5. Avoid FILTER(entire fact table, ...) in CALCULATE; filter columns. Use variables to avoid repeated calculations.
      6. Fewer visuals per page; each one is a separate query. Use bookmarks/drillthrough instead of 25 visuals on one page.
      7. For huge data: aggregations, incremental refresh, or DirectQuery/Direct Lake.

      Power BI interview questions

      Measure vs calculated column?

      A measure is evaluated at query time for the current filter context and isn't stored; a calculated column is computed per row at refresh and stored. Use measures for aggregations, columns for row attributes you slice by.

      Explain filter context and row context.

      Filter context is the set of filters active when a measure is evaluated (visual rows/columns, slicers, filters). Row context is the current row during iteration (calculated columns, SUMX). Row context doesn't filter; CALCULATE converts it into filter context (context transition).

      What does CALCULATE do?

      Evaluates an expression in a modified filter context: it can add, replace or remove filters, and triggers context transition.

      ALL vs ALLSELECTED vs ALLEXCEPT?

      ALL removes filters entirely; ALLSELECTED removes filters from inside the visual but keeps outside selections like slicers; ALLEXCEPT removes all filters on a table except the listed columns.

      Star schema vs snowflake? Why star in Power BI?

      Star: one fact table with denormalised dimension tables. Snowflake: dimensions normalised into sub-tables. Star gives simpler DAX, correct filter flow, better compression and speed.

      Import vs DirectQuery?

      Import copies data into the model: fastest and fully featured, refreshed on a schedule. DirectQuery queries the source live: fresher and handles huge data, but slower and with some limitations.

      Why do you need a date table, and how do you create one?

      Time intelligence needs a continuous, full-year calendar marked as a date table. Create it with DAX (CALENDAR + ADDCOLUMNS), Power Query, or the source; mark it; relate it to fact dates; turn off auto date/time.

      How do you implement row-level security?

      Define roles with DAX filters (static, or dynamic with USERPRINCIPALNAME and a mapping table), test with View as, then assign users/groups to roles in the service.

      What is a gateway and when do you need one?

      Software that securely connects the Power BI service to on-premises data sources for refresh or DirectQuery. Not needed for cloud sources.

      Dashboard vs report?

      A report is multi-page, interactive and built in Desktop on one semantic model. A dashboard is a single page of pinned tiles in the service that can combine tiles from multiple reports and supports alerts.

      Bidirectional relationships: when and why be careful?

      They let filters flow both ways, useful for some many-to-many or bridge scenarios, but can create ambiguous filter paths, unexpected results and slower performance. Prefer single direction and CROSSFILTER in a specific measure.

      A visual is slow. How do you troubleshoot?

      Performance Analyzer to see DAX vs rendering time; inspect the DAX in DAX Studio; check the model (cardinality, unused columns, bi-directional filters, calculated columns); simplify the measure (variables, column filters instead of FILTER on the fact table); reduce visuals per page.

      Practical: "Show revenue this year vs last year by month, with growth %."

      Date table marked and related; measures Revenue, Revenue LY with SAMEPERIODLASTYEAR, YoY % with DIVIDE; a line and clustered column chart with Calendar[Month] on the axis (sorted by Month No), Revenue and Revenue LY as columns, YoY % as the line.

      Relationships and pitfalls

      • Correlation (−1 to 1) measures how two variables move together. Correlation is not causation: ice-cream sales and drownings both rise in summer.
      • Simpson's paradox: a trend in every subgroup can reverse when groups are combined (because group sizes differ). Always check results by segment.
      • Survivorship bias: analysing only customers who stayed hides why others left.
      • Seasonality: compare December with last December, not November.
      • Base effects: "+200% growth" from 1 to 3 orders isn't news. Show absolute numbers next to percentages.
      • Percentage points vs percent: margin from 20% to 22% is +2 percentage points, or +10% relative.

      A/B testing basics

      1. Randomly split users into control (A) and variant (B); change one thing.
      2. Define the primary metric and the minimum effect worth detecting before starting.
      3. Run long enough for the required sample size (and full weekly cycles).
      4. A p-value below 0.05 means a difference this large would be unlikely if there were truly no effect. It is not the probability the variant is better.
      5. Check guardrail metrics (cancellations, complaints), not just the headline metric.

      Business-case rounds

      "Revenue dropped 10% last month. What would you do?" They want structure, not a magic answer: clarify, check the data, decompose the metric, segment, form hypotheses, recommend.

      A framework you can use for any metric question

      1. Clarify: which revenue (gross/net)? Compared to what (last month, last year, target)? Is 10% unusual for this business?
      2. Check the data: pipeline failures, late-arriving data, definition changes, duplicates. A surprising number is often a data problem.
      3. Decompose the metric: Revenue = Orders × AOV = (Visitors × Conversion) × (Items per order × Price per item). Which factor moved?
      4. Segment: by region, channel, category, new vs returning, device, product. Is the drop everywhere or concentrated?
      5. External and internal events: seasonality, holidays, competitor sale, price change, stock-outs, site outage, marketing spend cut.
      6. Hypothesise and test with data; quantify each factor's contribution.
      7. Recommend actions and how you'd monitor them.
